**Genesis versus Isaac Lab for the future HRC benchmark — 2026-09-09**

My recommendation is Isaac Lab as the primary long-term benchmark framework, with the human-motion generator kept simulator-independent. Genesis is a strong alternative for a compact research implementation, local development across hardware platforms, differentiable simulation, and experiments involving fluids or deformables. This is an engineering judgment about reusable capabilities, not a measured speed or physical-accuracy ranking.

This comparison uses official documentation and release notes, plus the previously inspected project implementations. No new simulator performance experiments were run. The benchmark scope is human-present mobile manipulation: avoidance, placement relative to a person, following, physical grasping, and VLA evaluation.

The previous implementation review favored the coworker's motion architecture. That does not imply that Genesis itself supplies that human intelligence: the coworker integrates TRUMANS and SMPL-X externally. That architecture can also feed an Isaac adapter.

**Version boundary**

Genesis's release page lists v1.4.0, whose `0ce793b` commit matches the coworker's engine submodule. Isaac Lab's latest listed release is `v3.0.0-beta2.patch1`; the 3.0 line remains explicitly beta. Many capabilities below are documented on moving `latest` or `develop` pages and are not a guarantee that the installed container exposes exactly those APIs. Pin and verify the chosen version before implementation. [Genesis releases](https://github.com/Genesis-Embodied-AI/genesis-world/releases), [Isaac Lab releases](https://github.com/isaac-sim/IsaacLab/releases).

Isaac Lab is a robot-learning framework. Its established PhysX path uses Isaac Sim; the 3.0 development line also offers Newton without a full Isaac Sim installation. Newton remains beta, and OvPhysX is highly experimental. Do not assume backend parity or that switching backends preserves contact behavior. [Backend comparison](https://isaac-sim.github.io/IsaacLab/develop/source/overview/core-concepts/physical-backends/index.html).

**What Genesis does not provide, or only supports conditionally**

- Its built-in `plan_path` rejects entities containing free or spherical joints. This is a planner limitation, not a physics limitation. It matters for a floating mobile base and potentially the coworker's kitchen entity containing free objects. A separate arm model, another planner or a suitable joint parameterization is needed. Planning is kinematic and is not a built-in reactive human-avoidance policy. [Planner limits](https://genesis-world.readthedocs.io/en/latest/user_guide/robot_control/path_planning.html).
- The standard camera sensor API currently returns RGB only; use other rendering/raycast APIs for depth or segmentation. Rasterizer environments render sequentially; the batch renderer is CUDA-only and requires common camera resolution. Do not infer fast visual rollouts from fast physics alone. [Camera restrictions](https://genesis-world.readthedocs.io/en/latest/user_guide/sensing/camera_sensors.html).
- Differentiation does not cover every contact/coupling path: elliptic friction and SAP coupling have documented restrictions, and long horizons increase memory use and gradient instability. [Autodiff limits](https://genesis-world.readthedocs.io/en/latest/user_guide/theory/differentiable_simulation.html).
- I did not verify a first-party task-authoring/demo-generation suite equivalent to Isaac's managers plus Mimic/SkillGen. Those workflows are feasible in Genesis but should be budgeted as integration work rather than counted as already delivered by the engine.
- Nyx is a separate dependency. The general guide still describes internal distribution, while the public plugin repository provides wheels and a `gs-nyx-plugin` install command. Use a tested plugin/engine pair; do not promise that the main package alone supplies every photorealistic-rendering feature. Public wheels target NVIDIA on Linux/Windows, not Apple Silicon. [Nyx guide](https://genesis-world.readthedocs.io/en/latest/user_guide/rendering/nyx_renderer.html), [Nyx plugin](https://github.com/Genesis-Embodied-AI/genesis-nyx).

**What Isaac Lab does not provide, or only supports conditionally**

- PhysX provides no physics gradients and no Cable Object API. Some underlying particle capabilities are not exposed through the standard Lab asset interface. Newton adds options, but its VBD/MPM paths are experimental and its multi-agent/self-play workflows are not yet wired up. A scripted human alongside one robot policy does not itself require a multi-agent learning API. [PhysX scope](https://isaac-sim.github.io/IsaacLab/develop/source/overview/core-concepts/physical-backends/physx/supported-features.html), [Newton limits](https://isaac-sim.github.io/IsaacLab/develop/source/overview/core-concepts/physical-backends/newton/supported-features.html).
- The full Isaac Sim/RTX path is not a native Mac workflow; its documented requirements exclude GPUs without RT cores such as A100/H100. This does not automatically exclude those GPUs from every kit-less Newton workload. [Hardware requirements](https://docs.isaacsim.omniverse.nvidia.com/latest/installation/requirements.html).
- Mimic needs annotated subtasks, object poses, action/EEF conversions and a correct success predicate. It can produce failed candidates and its documentation warns about replay nondeterminism. It does not automatically reproduce human reactions, intent or safety-aware timing. [Mimic requirements](https://isaac-sim.github.io/IsaacLab/develop/source/overview/imitation-learning/teleop_imitation.html).
- SkillGen needs additional planning dependencies and manual subtask boundaries. Collision-free planning depends on the supplied geometry; safe interaction with a moving person remains an extra problem. [SkillGen setup](https://isaac-sim.github.io/IsaacLab/main/source/overview/imitation-learning/skillgen.html).
- Force measurements require configuration care: PhysX stabilization can distort reported contact-force magnitudes. Contact-rich scenes may require GPU-buffer tuning. Treat these as measurement validity concerns for this benchmark. [PhysX caveats](https://isaac-sim.github.io/IsaacLab/develop/source/overview/core-concepts/physical-backends/physx/supported-features.html).

**Shared gaps relevant to this benchmark**

Neither reviewed stack provides a ready-made implementation of your exact human-present RoboCasa benchmark. Both still need task definitions, aligned observations/actions, success/failure semantics, human behavior, asset validation and benchmark splits. This is the boundary established by the current local implementations, not a claim that no external integration exists anywhere.

Human motion generation and physical hand manipulation are different components. Isaac Sim provides actor/animation and synthetic-data tooling, which may help background-person scenarios, but that is not evidence of a validated SMPL-X physical handover controller. The coworker's TRUMANS bridge likewise needs grasp/contact and reactive-behavior layers. [Isaac actor tooling](https://docs.isaacsim.omniverse.nvidia.com/latest/action_and_event_data_generation/tutorial_replicator_agent.html).

For avoidance, measure robot-versus-human geometry, not only joint centers. For handover, distinguish contact-supported grasp from an auxiliary spring/weld. For placement, verify release, stability and orientation where the task requires them. These definitions remain project work regardless of engine. Neither simulator selection guarantees correspondence with real human injury risk or exact reproduction of MuJoCo dynamics.

**How I would accelerate your benchmark design**

1. Keep one shared episode specification: task, layout/style, seed, robot, initial states, human-motion ID, reaction mode and policy-observation restrictions. Keep task predicates and human-motion files outside backend-specific code.
2. Use Isaac's manager-based environment for the first reusable task family. Reuse the same observation/action definitions and change only goal/reward/termination terms between avoid, follow and place-relative-to-human. Adapt the existing scripts rather than treating them as already complete Lab environments.
3. Port the coworker's motion schema to an Isaac human adapter. Start with the same prescribed trajectory and collision geometry on both backends; add reactive behavior later as a separately tested component. This preserves the coworker's useful work.
4. Integrate one manipulation task with Mimic, adding object-relative subtask boundaries and a strict final-state predicate. Generate robot-only seeds first; then add human timing variations with a safety-aware controller. Successful manipulation data alone does not teach yielding.
5. Build a shared recorder containing policy-visible RGB/state/action and evaluator-only human geometry, contacts, task state and failure reason. Keep privileged information out of VLA inputs unless explicitly allowed by the track. Define distinct state-policy and vision-policy tracks.
6. Batch repeated episodes of one validated layout first. Keep hot-loop tensors on the GPU, render only at policy cadence and batch VLA inference where supported. Profile simulation, rendering, human-motion inference, model inference and data writing separately before adding GPUs.
7. Retain a small Genesis regression set instead of maintaining full task parity immediately. Use it to test whether findings depend on one contact solver and to investigate different material models later.

For reproducibility, Genesis 1.4's self-contained rigid-scene/trajectory archives could shorten bug reporting between coworkers. Archive replay should not be confused with proving identical live simulation on arbitrary hardware. [Release feature](https://github.com/Genesis-Embodied-AI/genesis-world/releases).

**Decision rule**

Choose Isaac Lab for a long-lived, multi-task benchmark with VLA observations, demonstration generation, multiple baselines and eventual robot deployment. Choose Genesis if the immediate deliverable is a compact human-motion study, heterogeneous local hardware is central, or differentiable/multi-material physics is the main contribution.

Before investing in complete migration, run the same validated pick-and-place episode, then an avoidance episode, at batch sizes 1, 8 and 32 where memory permits. Compare full-task success, human collision/clearance, reset reliability, warm throughput, startup time and peak memory. Report successful valid episodes per GPU-hour and implementation effort; raw physics steps per second alone will not select the most productive benchmark platform.
